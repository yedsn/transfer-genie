# Design

## Context

移动端 Composer 是同一个 Vue/WKWebView 运行时内的全屏页面，并通过 UIKit 单 WebView 导航协调器完成 push/pop。当前原生 shown 回调已尝试聚焦编辑器，但文本输入没有稳定的组件引用，Markdown 编辑器又是异步加载；同时键盘态样式直接隐藏 mobile-compose-actions。桌面端已有默认格式和提交字段，但 Rust 设置模型此前没有持久化该字段；移动端初始化仍以会话字段或固定文本值为主。

## Goals / Non-Goals

**Goals:**

- 在原生页面 push 完成、编辑器可用且仍属于当前 Composer 请求时完成一次确定性的聚焦。
- 让编辑区负责吸收键盘造成的高度变化，底部操作区保持稳定可见。
- 复用现有设置保存接口和字段，并明确“恢复草稿优先于默认格式”的初始化顺序。
- 保持现有草稿安全门、附件选择、嵌套标记弹框和原生返回行为不变。

**Non-Goals:**

- 不重新设计 Composer 的整体视觉语言或 Markdown 工具条。
- 不新增编辑器格式、数据库迁移、第三方编辑器依赖或后台同步协议。
- 不保证 iOS 在脱离用户手势的任意异步时刻都接受软键盘请求；失败时保留正常的手动聚焦路径。

## Decisions

### 1. 以一个 Composer 聚焦函数统一文本与 Markdown 时序

在 MobileShell 中维护文本输入引用，并让 Markdown 编辑器在编辑视图创建完成时发出 ready 信号。统一的聚焦函数只在 Composer 仍为当前页面、草稿恢复已完成且控件未禁用时运行，并在以下两个入口调用：

1. 非原生或浏览器路径打开 Composer 后的 DOM flush；
2. 原生导航协调器发出当前 request ID 的 shown 事件后。

Markdown 异步组件未就绪时记录一次待聚焦意图，由 ready 信号消费；不使用持续轮询或重复定时 focus。

选择这一方案，是因为原生 push 结束前唤起键盘会让键盘几何与转场竞争，而只依赖 HTML autofocus 无法覆盖异步 Markdown 编辑器和 WKWebView 的用户手势限制。备选方案是每隔一段时间查找 DOM 并聚焦，但它容易抢走附件或标记弹框的焦点，也会破坏无障碍操作。

### 2. 默认格式在草稿恢复流程内一次性解析

Controller 读取设置后先把 default_editor_format 规范化为 text 或 markdown。恢复当前账号和存储空间的草稿时：

- 有草稿：使用草稿的 format；
- 无草稿：使用规范化后的设置值；
- 缺失或非法设置值：回退为 text。

不再让原生 Composer 页面通过独立 sessionStorage 值覆盖恢复结果。Composer 内主动切换格式仍由现有草稿监听和持久化逻辑保存。

选择这一方案可避免设置、页面会话和草稿三个来源互相覆盖。备选方案是每次打开页面都直接读取默认设置，但会错误改变已有 Markdown 或文本草稿。

### 3. 设置页使用紧凑的双选分段控件并立即持久化

在移动端“应用”设置组中增加与现有卡片视觉一致的行，行内提供“文本 / Markdown”双选控件，当前选项同时通过文字、选中状态和 aria-pressed 表达。切换时使用“读取最新设置—合并字段—保存”的现有模式，防止覆盖其他页面刚更新的设置。

Rust 设置模型增加可选的 default_editor_format，并纳入 iOS 设置合并及导入导出；非法值归一为文本。旧配置缺省时不强行写入默认值，以保留桌面端原有 localStorage 偏好的回退行为。此字段为各设备的应用设置，不表示通过 Supabase 跨设备同步。

保存期间禁用两个选项；成功后更新本地设置快照并显示全局 Toast；失败时恢复原值并显示错误 Toast。预览模式只更新内存并明确提示不会写入本机。

选择立即保存是因为这里只有两个互斥选项，移动端设置页没有统一的整页“保存”动作。单独增加设置弹框会增加一次无必要的导航层级。

### 4. Composer 固定为四段 flex 画布

全屏 Composer 保持固定画布和明确的滚动所有权：顶部页头、仅 Markdown 显示的格式工具条、可缩小且独立滚动的编辑区，以及始终占位的底部操作区。

删除键盘态隐藏 mobile-compose-actions 的规则，并让编辑区使用可缩小、独立滚动的 flex 布局，操作区不参与收缩。键盘高度继续优先使用 UIKit 报告的可见区域，避免重复扣减 VisualViewport offset。附件较多或辅助功能字体较大时，操作区内部采用有限滚动或紧凑布局，不能把根 WKWebView 变成滚动容器。

这满足“操作条一直在”的明确需求。虽然隐藏附件或发送区可以给键盘更多写作空间，但与本次交互目标冲突，因此不采用。

### 5. 分层验证真实键盘行为

浏览器测试验证格式优先级、设置保存、焦点意图和 CSS 可见性；Controller 测试验证有无草稿的初始化。最终必须在安装后的官方 iOS Simulator 中使用软件键盘验证文本和 Markdown 两种路径，因为浏览器自动化无法证明 WKWebView 真正显示了 iOS 键盘。

## Risks / Trade-offs

- iOS 可能拒绝原生转场完成后的程序化键盘请求 → 将聚焦绑定到用户点击发起的打开协议，并保留可见、可点击的编辑器；Simulator 和真机分别验收。
- Markdown 异步加载可能晚于原生 shown → 使用一次性 pending-focus 与 editor-ready 握手，不轮询 DOM。
- 常驻操作区会缩小小屏或横屏的写作高度 → 仅让编辑区缩小和滚动，并为大字体和横屏验证最小可用高度及操作区内部布局。
- 设置保存和其他设置更新并发可能覆盖字段 → 保存前读取最新设置并只合并 default_editor_format。
- 聚焦逻辑可能在返回附件选择器或关闭嵌套弹框时抢焦点 → 仅由首次打开请求或显式 editor-ready 消费对应 request ID，不在普通响应式更新中重复执行。

## Migration Plan

1. 先接入移动端设置读写和无草稿默认值，保留非法或缺失值回退为文本。
2. 接入统一聚焦握手和常驻操作区布局。
3. 运行前端、Controller 与草稿回归测试，再部署官方 Simulator 完成软件键盘测试。
4. 若原生键盘行为出现回归，可回滚聚焦握手与布局改动；现有设置字段和草稿数据无需迁移或回滚。
