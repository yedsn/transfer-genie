# Design

## Context

当前附件表已经具有 `preview_object_path`，Supabase 拉取逻辑也会保存该字段，但文件发送和存储空间数据传输始终把它写成空值。现有预览命令仅按 WebDAV 路径读取缩略图，无法从 Supabase Storage 获取预览。客户端已有图片压缩、视频抽帧、Storage 流式上传下载和附件可靠 outbox，可在这些能力上补齐链路。

消息列表目前为每个图片或视频直接请求预览，失败后隐藏图片元素；详情中的图片有本地原件时直接展示原件，没有一致的加载、失败和重试状态。设计需要同时处理跨设备可用性、历史附件迁移、私有对象权限和长列表性能。

## Goals / Non-Goals

**Goals:**

- 将图片缩略图和视频封面作为附件的独立派生对象可靠发布到 Supabase。
- 让另一设备只获取小尺寸预览即可渲染列表，并在本地隔离缓存。
- 为历史附件提供渐进补全，不要求用户重新执行整库传输。
- 为所有文件类型提供统一、稳定、有状态的列表卡片和详情体验。
- 复用现有本地优先、outbox、RLS 和 Storage 能力，不引入第二套同步体系。

**Non-Goals:**

- 第一阶段不在应用内渲染 PDF、Word、Excel 或 PowerPoint 的页面内容。
- 第一阶段不解析压缩包目录，也不为音频生成波形图。
- 不公开 Supabase bucket，不在数据库保存签名 URL。
- 不在应用启动后自动全量下载所有历史原件来生成预览。
- 不改变 WebDAV 现有远端预览布局，但前端统一预览状态可以同时改善 WebDAV 展示。

## Decisions

### 1. 预览是附件的独立派生对象

每个可视觉预览的附件使用稳定对象目录：

```text
<user-id>/<space-id>/<attachment-id>/<original-name>
<user-id>/<space-id>/<attachment-id>/preview.jpg
```

`attachment_sync.object_path` 指向原件，`attachment_sync.preview_object_path` 指向预览。预览统一输出受限尺寸 JPEG，沿用现有图片缩放和视频抽帧实现。稳定路径允许上传结果未知时安全覆盖重试，也便于附件删除时清理整个附件目录。

备选方案是保存 data URL、签名 URL，或把缩略图存入数据库。它们会增加数据库体积、引入 URL 过期问题或绕开现有 Storage 权限，因此不采用。

### 2. 原附件同步与预览发布解耦

原附件继续通过现有附件 outbox 上传并提交元数据。预览在本地原件可靠保存后生成，可以与原件上传并行准备，但预览失败不阻止原附件完成。

预览成功上传后，通过新的附件元数据更新操作或对现有附件操作的可恢复扩展写入 `previewObjectPath`。更新必须使用稳定 operation ID、payload hash 和 base revision；若预览在首次附件提交前已经准备好，可直接包含在首次 payload 中。

备选方案是要求原件和预览全部成功后才提交附件。这会让 FFmpeg 缺失、格式损坏或预览网络失败阻断正常文件发送，因此不采用。

### 3. Supabase 预览读取统一进入 Provider 感知的解析流程

后端预览解析顺序为：

1. 检查当前存储空间、账号和附件 ID 对应的本地预览缓存。
2. WebDAV 空间沿用现有新旧缩略图路径兼容逻辑。
3. Supabase 空间从 `attachment_sync.preview_object_path` 获取稳定路径并使用当前 Session 下载。
4. Supabase 历史附件没有预览路径时，进入懒补全流程。
5. 不支持视觉预览或补全失败时，向前端返回结构化状态，而不是仅返回“预览不存在”。

预览接口应返回至少包含 `state`、`kind`、可选本地路径和可选错误信息的结果，使前端能区分 `ready`、`loading`、`unsupported`、`offline` 和 `failed`。为了兼容现有调用，可以先新增命令或让调用方同步迁移后再替换旧字符串返回值。

备选方案是在前端直接拼接 Storage URL。私有对象需要 Session、RLS、缓存和错误治理，放在 Rust Provider 层更安全且可复用，因此不采用。

### 4. 历史附件采用按需懒补全

当图片或视频附件缺少 `preview_object_path` 且预览进入可视区域或详情需要时：

- 优先使用附件隔离目录中的本地原件。
- 没有本地原件时，把云端原件流式写入专用临时缓存，校验完成后生成预览。
- 上传 `preview.jpg`，再通过权威附件操作更新预览路径。
- 临时原件不写入用户下载目录，也不计为正式下载；任务结束后按缓存策略清理。
- 同一附件以单飞任务合并多处请求。

备选方案是发布后立即执行全量后台迁移。它可能在没有明确提示时大量消耗网络、磁盘和 CPU，并且很难暂停恢复，因此不作为默认行为。以后可以增加用户主动触发、带进度的“补全历史预览”。

### 5. 文件预览分为真实缩略图和类型卡片

第一阶段支持矩阵：

| 类型 | 列表 | 详情 |
|---|---|---|
| 图片 | JPEG 缩略图 | 先显示缩略图，打开时按需原图 |
| 视频 | JPEG 封面和播放标识 | 封面后按需准备播放器 |
| 音频 | 音频类型卡和播放入口 | 沿用按需播放 |
| 文档、PDF、代码文件 | 扩展名和类型卡 | 文件信息、下载并打开 |
| 压缩包、未知文件 | 通用类型卡 | 文件信息、下载并打开 |

类型判断继续以 MIME 和扩展名共同完成。真实缩略图使用固定容器、骨架占位和 `object-fit`，加载失败回退到类型卡而不是移除整个预览区域。

### 6. 缓存键和并发控制包含完整归属

预览缓存路径和内存任务键使用：

```text
<profile-id>/<owner-scope>/<attachment-id>/<preview-version>.jpg
```

其中 `owner-scope` 对 Supabase 为 Auth 用户 ID。预览路径或远端 revision 变化时更新版本，避免继续展示旧内容。生成并发沿用或扩展现有预览信号量；下载使用独立的小并发队列。前端使用可视区域观察器触发请求，后端对相同键执行 single-flight 合并。

仅使用消息文件名作为缓存键会在账号、空间或重复文件名之间产生碰撞，因此不采用。

### 7. 存储空间数据传输也生成目标侧预览

传输到 Supabase 时，目标附件 ID 和原件对象路径仍由目标空间确定。若来源存在可用本地预览，可在验证归属和格式后复用其字节并上传到目标预览路径；否则在目标缓存中的原件完成校验后生成预览。附件导入操作最终写入目标 `previewObjectPath`，失败则留下独立可恢复的补全状态，不把整个传输项目标记失败。

不直接复制来源的 `preview_object_path`，因为来源可能属于不同 Provider、账号、空间或 RLS 路径。

## Risks / Trade-offs

- 历史视频首次生成封面可能下载较大原件 → 只在预览进入需要状态时执行，显示明确状态，限制并发并允许取消尚未开始的任务。
- FFmpeg 不可用或视频格式不受支持 → 回退类型卡，不阻塞附件同步，并记录可重试错误。
- 原件已上传但预览元数据更新冲突 → 使用附件 revision 和稳定 operation ID 重试，冲突时重新拉取后判断远端是否已经包含等价预览路径。
- 多设备同时补全同一历史预览 → 使用相同稳定对象路径，上载可幂等覆盖；元数据操作仍按 revision 处理，已存在等价路径时视为完成。
- 预览缓存持续增长 → 删除消息时清理关联缓存，并为后续按容量或最近使用时间清理保留统一目录结构。
- JPEG 不能保留 GIF 动画或透明背景 → 列表预览以轻量静态图为目标，完整效果仍通过按需打开原文件获得。

## Migration Plan

1. 先增加本地查询、结构化预览状态和 Supabase 预览下载能力，同时保持现有 `preview_object_path` 为空的数据可正常显示类型卡。
2. 增加新发送和传输流程的预览生成、上传及元数据提交，验证新附件可跨设备显示。
3. 启用历史附件懒补全；以空路径作为未迁移状态，不执行破坏性数据库迁移。
4. 更新列表和详情 UI，启用懒加载、占位、失败回退和重试。
5. 增加删除清理、账号隔离、并发和跨设备回归测试。

回滚时可以停止生成和请求预览对象，原附件路径与下载逻辑保持有效。已写入的 `preview_object_path` 和 Storage 预览对象可以保留，旧客户端会忽略该字段；如需清理，应通过受控的附件对象清理流程完成。
