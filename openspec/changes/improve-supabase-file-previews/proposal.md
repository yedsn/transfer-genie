# Proposal

## Why

Supabase 附件虽然已经上传原文件，但客户端没有生成、上传和读取独立的云端预览对象，导致图片和视频在其他设备上没有缩略图，历史附件也只能显示文件名。需要补齐完整预览链路，并让所有文件类型在列表和详情中都有稳定、一致且不会触发完整原件下载的预览体验。

## What Changes

- 为 Supabase 图片和视频附件生成独立 JPEG 预览对象，上传到私有 Storage，并在附件元数据中保存稳定的 `preview_object_path`。
- 在 Supabase 设备间同步后按需下载、缓存和复用预览对象；消息列表加载预览时不得下载完整原文件。
- 新上传、语音之外的文件发送以及存储空间数据传输统一保留原附件和预览对象之间的关联。
- 对没有云端预览的历史图片和视频采用懒补全：首次需要预览时基于本地原件或临时获取的云端原件生成并回传预览。
- 为图片、视频、音频、文档、压缩包和未知文件提供统一的预览卡片、加载占位、失败提示和重试行为；图片和视频显示真实缩略图，其余类型使用文件类型卡片与现有按需打开或播放能力。
- 预览缓存按存储空间、Supabase 账号和附件稳定 ID 隔离，并对并发生成、并发下载和重复请求进行限制与合并。
- 预览生成或上传失败不阻塞原附件发送与同步，并保留可重试状态。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `message-feed`: 扩展文件消息列表和详情的预览行为，使所有文件具有稳定预览卡片，并让图片和视频使用按需加载的真实缩略图。
- `supabase-storage`: 扩展私有附件生命周期，加入预览派生对象的上传、元数据同步、读取、删除和历史补全。
- `local-first-sync`: 规定预览缓存隔离、失败降级、并发去重和预览补全的可恢复同步行为。

## Impact

- Rust：`src/main.rs`、`src/db.rs`、`src/media_preview.rs`、`src/supabase_sync.rs`，以及相关测试和 Supabase RPC/SQL 定义。
- 前端：`src-ui/src/legacy-main.js`、媒体类型工具、消息列表与预览弹窗样式。
- 本地数据：复用现有 `attachment_sync.preview_object_path`，补充查询、缓存状态和必要的迁移兼容逻辑。
- Supabase：复用私有 `transfer-genie-files` bucket 与现有 RLS 路径约束；附件 RPC 需要可靠保存和传播预览对象路径。
- 性能：列表只传输小尺寸预览；历史补全按需执行并限制并发，不进行无提示的全量原件下载。
