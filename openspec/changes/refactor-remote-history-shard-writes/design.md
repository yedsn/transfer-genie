## 背景

Transfer Genie 使用 SQLite 保存本地消息状态，但 WebDAV 仍是跨设备共享消息文件和远端元数据的来源。当前 manifest 布局已经通过 `history/index.json`、按月拆分的 `history/shards/{YYYY-MM}.json` 和 `history/tags.json`，避免了早期单个 `history.json` 持续膨胀的问题。

剩余瓶颈主要在写入路径。常见操作会加载全部远端历史并调用 `save_history`，即使只改了一条消息或一个月份，也会重新去重、分组并上传所有分片。受影响的流程包括发送、标记、标签分配、置顶切换、删除、清理、Telegram Bridge 追加历史以及同步修复。

## 目标与非目标

**目标：**

- 消息级远端历史写入只触碰受影响的分片文件。
- 保留现有 manifest 布局和本地 SQLite 表结构。
- 继续读取遗留 `history.json`，并能在需要写入时转换为 manifest 布局。
- 保持与已支持 manifest 格式的现有客户端同步行为兼容。
- 将全量历史重写收敛为明确的修复/迁移路径，而不是默认写入路径。

**非目标：**

- 不引入远端 SQLite 或其他服务端数据库文件。
- 不把远端元数据拆成“每条消息一个 JSON 文件”。
- 不改变 WebDAV `files/{YYYY}/{MM}/...` 消息文件布局。
- 不新增用户可见的设置项、界面控件或 API 变更。
- 不在本次变更中重新设计多端并发写入冲突检测；仍沿用当前 sync guard 和 WebDAV 元数据策略。

## 设计决策

### 1. 保持 manifest 分片作为远端元数据单位

决策：继续使用 `history/index.json` 和 `history/shards/{YYYY-MM}.json` 作为 WebDAV 上的持久化元数据布局。

原因：按月分片能在本地解析成本和 WebDAV 请求数量之间取得平衡。每条消息一个文件虽然能降低单条写入成本，但会在同步和 Bridge 扫描时显著增加 WebDAV 请求延迟。远端 SQLite 文件也不适合多设备通过 WebDAV 直接更新，合并和锁语义都不可靠。

备选方案：
- 每条消息一个 JSON 元数据文件：不采用，因为 WebDAV 请求数量会随消息数量增长。
- 远端 SQLite：不采用，因为 WebDAV 不提供跨客户端数据库锁语义。
- 继续全量 `save_history` 写入：不采用，因为小修改仍会按总历史规模付出成本。

### 2. 新增按分片作用域的历史变更辅助方法

决策：新增 history API，用于加载 manifest 索引、根据条目时间戳识别受影响的分片 key、只下载这些分片、应用变更，并且只在分片引用变化时上传变更分片和 `index.json`。

预期辅助方法：
- 追加或 upsert 一个或多个 `HistoryEntry`。
- 按 filename 删除历史条目。
- 按 filename 更新消息标记、标签分配和置顶等元数据。
- 当消息条目无需变化时，单独通过 `history/tags.json` 更新标签目录。

现有 `save_history` 保留，用于迁移、修复和全量重建流程。

### 3. 将遗留布局和不一致布局作为修复场景处理

决策：如果某个 WebDAV 端点只有遗留 `history.json`，或 manifest 索引用到了缺失/损坏的分片，写入路径可以在加载可恢复历史后回退到全量 manifest 重建。

原因：局部写入依赖可信的索引到分片映射。回退到重建路径可以保持兼容性，也让修复行为更直接。

### 4. 保持缓存行为兼容

决策：同步读取继续使用条件下载和缓存元数据。局部写入后，需要更新或失效化受影响远端路径对应的本地缓存元数据，避免下一次同步复用过期分片内容。

原因：局部远端写入后，本地 `history-cache/` 中的副本可能比已上传分片更旧。实现时可以在拿到响应头时同步写入缓存和元数据，也可以删除受影响路径的元数据，让下一次同步重新下载。

### 5. 按操作类型替换调用点

决策：高频操作点不再默认全量写历史，而是替换为与操作匹配的最小范围 mutation API。

映射关系：
- 发送文本/文件、Telegram 入站消息：append/upsert 当前消息所在分片。
- 标记/取消标记、置顶切换：更新该消息已存在的分片。
- 批量标签分配：按分片聚合选中的 filename，只写受影响分片。
- 标签创建/重命名：除非消息条目也要变化，否则只写 `history/tags.json`。
- 标签删除：写 `history/tags.json`，并且只清理引用了该标签的消息所在分片。
- 远端删除/清理：从受影响分片移除 filename，并更新 `index.json` 计数。
- 同步时从 `files/` 发现缺失历史条目：优先对发现条目执行 append/upsert；仅在修复遗留/不一致历史时全量重建。

## 风险与取舍

- [索引计数或时间范围过期] -> 上传 `index.json` 前，根据每个已变更分片重新计算 shard ref。
- [消息时间戳变化导致条目跨分片移动] -> mutation helper MUST 从旧分片移除该条目，并插入新分片。
- [遗留历史转换仍需全量读写] -> 将其保留为受控迁移路径，并添加测试覆盖。
- [多设备并发仍可能覆盖远端元数据] -> 本地继续使用现有 sync guard；本次不宣称提供跨设备事务写入。优先使用幂等 upsert/remove，并保持现有冲突行为。
- [本地写入后缓存元数据过期] -> 对受影响分片、`history/index.json` 和 `history/tags.json` 失效化或刷新缓存项。
- [辅助 API 增多导致复杂度上升] -> 将 helper 限定在 `history.rs` 内部，并为每类 mutation 写行为测试。

## 迁移计划

1. 在 `src/history.rs` 增加按分片读写的基础方法，同时保持现有 `load_history_*` 和 `save_history` 行为。
2. 将调用点逐步从 `load_history_with_layout` + `save_history` 替换为新的 mutation API。
3. 保留 `save_history`，用于遗留历史转换、manifest 修复、恢复流程和测试准备。
4. 添加回归测试，证明常见操作不会上传未受影响分片。
5. 回滚策略：由于远端 manifest 布局不变，调用点可回退到 `save_history`，无需迁移远端数据格式。
