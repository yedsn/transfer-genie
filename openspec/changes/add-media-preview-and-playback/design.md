# Design

## Context

当前图片上传链路使用 `image` 生成 JPEG 缩略图，并通过 `files/.thumbs/` 保存远端预览资源；消息列表、图片预览和批量下载弹框已经能够按 `filename` 调用 `get_thumbnail`。该任务目前在文件上传完成后异步读取上传源路径，对于 `send_file_data` 等使用临时文件的入口，临时文件可能在后台任务读取前被删除。

普通音频和视频只有原文件，没有统一预览或播放命令。语音转写源音频已有一个按需完整下载至 `source-audio` 缓存的命令和 HTML 音频播放器，可作为通用媒体缓存的参考。批量下载资料模型已经能够分类图片、音频和视频，但只为图片请求缩略图。参见 `proposal.md`、`specs/media-preview-playback/spec.md`、`specs/message-feed/spec.md` 和 `specs/bulk-download-dialog/spec.md`。

## Goals / Non-Goals

**Goals:**

- 让所有复用文件发送核心的入口使用同一套图片/视频预览图生成流程。
- 用统一稳定键定位远端预览图、本地预览图和媒体播放缓存，避免界面各自维护缓存规则。
- 在不污染正式下载目录、下载历史和下载状态的前提下，为音视频提供按需应用内播放。
- 保持媒体控件与消息选择、批量下载选择和矩形框选手势互不干扰。
- 兼容已有图片 `.thumbs`，并允许没有预览资源的旧媒体安全回退。

**Non-Goals:**

- 第一版不提供远端 Range 代理、边下载边播放或任意位置立即拖动。
- 不自动转码不受 WebView 支持的媒体格式。
- 不自动下载全部旧视频来补生成封面。
- 不生成音频波形、频谱或媒体内容分析信息。
- 不把预览缓存视为用户正式下载，也不把预览缓存暴露为下载目录。

## Decisions

### Decision: 使用统一版本化预览资源而不是继续按原扩展名存缩略图

新增预览路径采用稳定消息标识派生的版本化 JPEG 文件，例如 `files/.previews/v1/<年月>/<filename>.jpg`；本地缓存按端点隔离并使用相同逻辑。所有新图片和视频预览都使用此路径，读取图片时若新版资源不存在，再回退到现有 `files/.thumbs/.../<filename>`。

显式 `.jpg` 后缀避免现有 `.thumbs` 中“内容为 JPEG、文件名仍是原扩展名”的歧义，也便于后续提高生成策略版本而不覆盖旧缓存。替代方案是直接复用 `.thumbs`；该方案无法清楚区分视频封面、旧图片缩略图和生成版本，因此不采用。

### Decision: 在稳定本地缓存文件准备完成后生成预览图

发送核心在原文件上传成功后已经把文件复制到端点隔离的本地文件目录。预览任务 SHALL 使用该稳定缓存路径，而不是上传调用方传入的临时路径。对于不希望长期保留原文件的入口，至少需要在启动预览生成任务前读取所需数据或把临时文件所有权交给后台任务，完成后再清理。

预览生成和上传继续作为不阻塞发送结果的后台任务，但本地预览写入与远端上传均记录可诊断日志。替代方案是在上传前同步生成所有预览图；它会增加发送前等待时间，视频提帧对大文件尤其明显，因此不采用。

### Decision: 视频封面通过受控 FFmpeg sidecar 生成

应用打包一个经过版本固定的 FFmpeg 可执行文件，后端使用无交互子进程从视频较前位置提取一帧，再缩放、自动旋转并输出 JPEG。提帧超时、退出失败或不支持的格式均视为预览生成失败，不影响原文件上传。命令参数使用独立参数传递，不拼接 shell 字符串。

前端 Canvas 提帧只能覆盖用户在页面选择的本地视频，不能一致覆盖 HTTP、Telegram 等入口；依赖用户自行安装 FFmpeg 会产生不可控环境差异；引入完整 Rust 视频解码栈会显著增加集成复杂度。因此选择随应用分发的 sidecar。实现阶段需要为 Windows、macOS 支持的目标架构准备对应二进制并检查发布许可清单。

### Decision: 预览图命令升级为通用媒体预览解析

后端提供按端点和资料稳定标识解析预览图的命令。解析顺序为：新版本地缓存、新版远端资源、旧版图片本地缓存、旧版图片远端资源、类型占位错误。命令参数包含或能够解析目标端点，避免用户切换端点后异步响应串到错误资料。

前端消息列表与批量弹框共用有限并发的懒加载队列；可见元素退出或被重新渲染时忽略过期响应。替代方案是继续只传 `filename` 并依赖当前活动端点；它在端点快速切换和并行弹框请求下存在竞态，因此不采用。

### Decision: 通用媒体播放缓存独立于下载历史

后端增加 `resolve_media_playback_source` 一类命令，输入稳定资料描述并返回本地播放路径及来源类型。解析顺序为：

1. 上传后保留的本地原文件；
2. 已完成正式下载且文件仍存在；
3. 完整的端点隔离播放缓存；
4. 从 WebDAV 完整下载到临时文件，校验完成后原子移动进播放缓存。

播放缓存位于应用数据目录下的端点专属 `media-preview` 区域，不写 `download_history`，不更新消息 `local_path`，也不改变批量资料的 `downloaded` 状态。并发请求使用“端点 + 稳定资源键”去重，同一媒体只运行一个缓存任务，并通过独立事件报告缓存进度。失败或应用退出时清理未完成的临时文件。

替代方案是直接调用现有正式下载命令；该方案会污染用户下载目录、冲突规则和下载历史，无法满足预览语义，因此不采用。

### Decision: 第一版完整缓存后播放，不建立本机流媒体代理

HTML `<audio>`/`<video>` 使用 Tauri asset URL 加载解析出的本地文件。远端文件在完整缓存前显示加载进度，不把不完整路径交给播放器。

现有 WebDAV 层虽然支持从偏移位置继续下载，但播放器随机读取需要一个支持 HTTP Range 的本机代理，并涉及多区间请求、认证转发、缓存一致性和生命周期管理。为了控制第一版风险，选择完整缓存后播放；后续若实际视频体积证明等待不可接受，再单独提案增加 Range 流式播放。

### Decision: 前端使用单一媒体会话协调播放器

建立窗口级媒体会话管理器，记录当前活动的音频或视频元素、资源键、所属界面及清理回调。开始新播放、切换端点、翻页、切换分类、关闭弹框或移除待上传附件时，统一暂停并清空旧媒体源。

批量下载资料卡内的播放按钮和播放器容器使用明确的交互排除标记；卡片点击和矩形框选入口忽略来自媒体控件的 Pointer Events。视频统一在独立预览层播放，音频可使用卡片内紧凑控件，避免视频播放器改变网格尺寸。

替代方案是每个组件独立管理播放器；该方案容易出现多个媒体同时发声、缓存任务重复和弹框关闭后仍播放，因此不采用。

### Decision: 运行时解码能力决定是否播放，分类不等于保证支持

后端和资料模型继续根据扩展名/MIME 分类音频和视频；前端用浏览器媒体能力和播放器错误事件判断是否能够应用内播放。常见 MP3、WAV、M4A/AAC、MP4/H.264、WebM 作为主要验证格式，MKV、AVI、FLV、WMV、WMA 等只保证被正确分类，不承诺 WebView 可解码。

不支持时显示明确提示并保留下载/系统打开。第一版不加入转码任务，避免额外磁盘、CPU、编解码器许可与质量策略复杂度。

### Decision: 缓存清理使用容量、访问时间和归属删除三条规则

预览图和播放缓存保存最后访问时间或从文件修改时间推导近似访问顺序。启动后或写入新缓存后执行轻量维护，在容量超过内部上限时从最旧且未被当前播放器使用的文件开始清理。删除消息时按端点和资源键删除能够确定归属的本地缓存；选择本地+远端删除时同时尝试删除新版预览资源和兼容的旧图片缩略图。

缓存清理失败只记录日志，不阻止消息删除或应用退出；任何清理路径都必须限制在应用管理的端点缓存目录内。

## Risks / Trade-offs

- [FFmpeg sidecar 增大安装包并增加多平台发布复杂度] → 固定精简构建与版本，逐目标架构验证，更新发布文档和许可证清单。
- [视频提帧可能在异常或超大媒体上长期占用资源] → 设置进程超时、输出大小限制和单独后台并发上限，超时后回退类型图标。
- [完整缓存后播放导致大视频等待时间较长] → 展示明确缓存进度、支持取消、复用缓存；把 Range 播放留作后续独立能力。
- [播放缓存占用磁盘空间] → 设置内部容量上限、按最近使用清理并允许消息删除联动清理。
- [远端预览资源命名迁移导致旧客户端看不到视频封面] → 原文件和 history 不变；新版客户端兼容旧图片缩略图，旧客户端继续安全显示文件类型。
- [多个界面同时请求同一媒体造成重复下载] → 后端按稳定资源键去重缓存任务，前端由单一媒体会话协调播放。
- [异步预览响应在切换端点后污染当前视图] → 所有命令携带端点/资源身份，前端检查渲染代次后再应用结果。
- [媒体控件和批量框选冲突] → 使用交互排除标记、Pointer Events 测试和实机拖动/进度条验证。
- [恶意文件触发解码器漏洞] → 固定并及时更新媒体工具版本，以受限参数和超时运行；预览失败不自动重试循环。

## Migration Plan

1. 增加新版预览路径、端点隔离缓存目录和兼容读取逻辑，保留现有 `.thumbs` 行为。
2. 集成并验证 FFmpeg sidecar，先实现本地视频提帧与失败回退，再接入后台上传。
3. 修改上传核心使用稳定本地源生成图片和视频预览，验证文件路径、内存数据、HTTP 及其他入口。
4. 增加通用播放源解析、缓存去重、进度事件和缓存维护，不接入界面前先完成后端测试。
5. 依次接入待上传附件、消息列表、消息预览和批量下载弹框，并加入单一媒体会话管理。
6. 在支持格式、无预览资源、网络失败、大文件和端点切换场景完成自动化与桌面验证。
7. 若需要回滚，可关闭新媒体控件和新版预览生成；原始文件与 history 不受影响，新版 `.previews` 和本地缓存可保留或安全清理。
